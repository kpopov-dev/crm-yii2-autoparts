# Архитектура

## Слои и зависимости

```
HTTP → Controller → Form → Service → Repository → MySQL
                       ↓        ↓
                    Policy   EventPublisher → outbox → RabbitMQ → Consumer → Handler
```

Зависимости направлены строго внутрь. Контроллер знает о сервисе, сервис — об
интерфейсах репозиториев и публикатора событий, репозиторий — только о соединении с
базой. Обратных связей нет: репозиторий ничего не знает о HTTP, сервис — о формате
ответа API.

### Controller

`backend/modules/crm/controllers`. Тонкий слой: принимает запрос, проверяет право
через RBAC, отдаёт данные форме, вызывает сервис, возвращает массив. Сервисы приходят
через конструктор — Yii2 резолвит их из DI-контейнера.

```php
public function __construct($id, $module, DealService $deals, array $config = [])
```

### Form

`backend/modules/crm/forms`. Наследники `yii\base\Model` с типизированными
публичными свойствами. Отвечают за две вещи: белый список принимаемых полей и
валидацию формата. Фильтры сортировки ограничены `in`-правилом, поэтому в SQL не
может прийти произвольная строка.

### Service

`backend/services`. Здесь живут бизнес-правила и границы транзакций. Сервис решает,
что считать корректной сменой стадии заказа, когда писать историю и какое событие
опубликовать. Наружу возвращает массивы, а не ActiveRecord, — представление не зависит
от схемы таблиц.

### Repository

`backend/repositories`. Только чтение, только ручной SQL через `createCommand` с
именованными параметрами. Каждый репозиторий реализует интерфейс из
`domain/Contract`, поэтому сервис можно тестировать с подставной реализацией.
Метод `hydrate` превращает строку таблицы в стабильный контракт для API:
snake_case базы наружу не протекает.

### Domain

`backend/domain`. Слой без зависимостей от фреймворка:

- `Enum` — стадии заказа, статусы задач, роли, имена событий. Реализованы как
  `final class` с константами и статическими методами, чтобы список стадий и их
  подписи имели единственный источник истины.
- `Policy/StageTransitionPolicy` — конечный автомат воронки.
- `Dto` — `Pagination` с ограничением лимита, `PagedResult` с метаданными,
  `EventMessage` с генерацией UUID v4, `DateRange` с безопасным разбором дат.
- `Exception` — доменные исключения, которые `ApiExceptionFormatter` превращает в
  корректные HTTP-коды: 422 для валидации, 404 для отсутствующей сущности,
  409 для запрещённого перехода стадии.

Именно этот слой покрыт юнит-тестами — он не требует ни базы, ни брокера. Здесь же
находится единственное место, которое пришлось бы менять при переносе CRM в другую
предметную область: подписи стадий и правила движения по воронке.

## Внедрение зависимостей

`backend/config/container.php` описывает привязки интерфейсов к реализациям:

```php
DealRepositoryInterface::class => DealRepository::class,
EventPublisherInterface::class => OutboxEventPublisher::class,
```

Замена публикатора на прямую отправку в RabbitMQ или репозитория на реализацию
поверх другой СУБД — это правка одной строки конфигурации, а не бизнес-кода.

Соединение с базой зарегистрировано синглтоном, поэтому репозитории получают
`yii\db\Connection` через конструктор и не обращаются к `Yii::$app` изнутри.

## Схема базы данных

```
user ──┬──< client ──< deal ──< deal_stage_history
       │                 │
       ├──< deal         └──< task
       ├──< task
       ├──< notification
       └──< daily_stat

outbox_message      processed_message
(очередь событий)   (журнал идемпотентности)
```

Ключевые решения:

- Все временные метки — `INT` с unix-временем. Это упрощает сравнение диапазонов и
  позволяет использовать индекс на `created_at` без вызова функций над колонкой.
- Денежные значения — `DECIMAL(14,2)`, без чисел с плавающей точкой.
- Внешние ключи с `RESTRICT` на справочные связи и `CASCADE` на подчинённые записи:
  удалить менеджера, за которым числятся заказы, нельзя, а удаление заказа уносит
  его историю и задачи.
- `daily_stat` — витрина, которую инкрементально обновляет консьюмер. Отчёт за год
  не пересчитывает миллионы строк заказов.

Полный список индексов и обоснование — в [SQL.md](SQL.md).

## Модель прав

RBAC на `yii\rbac\DbManager`. Разрешения назначаются действиям, а не ролям в коде:

```
manager: client.view, client.manage, deal.view, deal.manage,
         task.view, task.manage, report.view
admin:   всё перечисленное + user.manage
```

Проверка выполняется в контроллере через `requirePermission`. Дополнительно
`scopeToUser` подменяет фильтр так, чтобы менеджер видел только свои записи —
ограничение накладывается на уровне SQL-условия, а не фильтрацией результата в PHP.

## Обработка ошибок

`ApiExceptionFormatter` реализует `BootstrapInterface` и подписывается на
`Response::EVENT_BEFORE_SEND`. Любое исключение превращается в единообразный ответ:

```json
{ "success": false, "message": "Переход из стадии \"won\" в стадию \"new\" запрещён", "code": 409 }
```

Ошибки валидации дополнительно содержат `errors` с разбивкой по полям — фронтенд
показывает их рядом с полями формы. В production стектрейсы наружу не попадают.

## Фронтенд

Vue 2.7 с Options API, Vuex и Vue Router 3. Состояние разделено на модули
`auth`, `dictionaries`, `notifications`; данные конкретных экранов живут в самих
компонентах, чтобы не раздувать глобальный стор.

HTTP-клиент — тонкая обёртка над `fetch` на чистом JavaScript, без axios.
Она подставляет заголовок `Authorization`, собирает query-строку, разбирает ошибки
в класс `ApiError` с полями `status` и `errors` и очищает токен при 401.

Перетаскивание карточек на канбан-доске сделано на нативном HTML5 Drag and Drop —
без внешних библиотек. Отпускание карточки вызывает `POST /api/deals/{id}/stage`,
и если сервер отклонил переход, доска перезагружается, а ошибка показывается
пользователем.
