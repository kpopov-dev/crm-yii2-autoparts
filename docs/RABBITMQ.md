# Асинхронная обработка событий

## Зачем это здесь

Смена стадии заказа должна быть быстрой для менеджера. Всё, что не обязано
происходить синхронно — уведомления, пересчёт витрины статистики, в перспективе
письма и интеграции — вынесено в очередь. Пользователь получает ответ сразу,
побочные эффекты обрабатываются воркерами.

## Топология

```
                    exchange crm.events (topic, durable)
                                │
        ┌───────────────────────┴───────────────────────┐
        │ deal.*, task.*                    deal.*      │
┌───────▼──────────────┐              ┌─────────────────▼─┐
│ crm.notifications    │              │ crm.analytics     │
│ durable, DLX         │              │ durable, DLX      │
└───────┬──────────────┘              └─────────┬─────────┘
        │ при nack                              │ при nack
        └──────────────┬────────────────────────┘
                       ▼
          exchange crm.events.dlx (fanout)
                       │
                       ▼
              crm.dead-letter
```

Топология объявляется в коде (`backend/messaging/Topology.php`) при каждом
подключении. Объявление идемпотентно, поэтому ручная настройка через веб-интерфейс
RabbitMQ не требуется — очереди появятся сами при первом запуске воркера.

Обменник типа `topic` выбран сознательно: добавить новую очередь, слушающую,
например, только `deal.won`, можно без изменения кода публикации.

## События

| Имя | Когда публикуется | Ключевые поля |
| --- | --- | --- |
| `deal.created` | создан заказ | `dealId`, `number`, `amount`, `responsibleId` |
| `deal.stage_changed` | сменилась стадия | `stageFrom`, `stageTo`, `changedBy` |
| `deal.won` | заказ отгружен | `amount`, `currency`, `responsibleId` |
| `deal.lost` | клиент отказался | `stageFrom`, `responsibleId` |
| `task.assigned` | создана или переназначена задача | `taskId`, `assigneeId`, `dueAt` |
| `task.completed` | задача выполнена | `taskId`, `authorId` |

Формат сообщения:

```json
{
  "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "name": "deal.stage_changed",
  "payload": { "dealId": 42, "stageFrom": "proposal", "stageTo": "negotiation" },
  "occurredAt": 1770000000
}
```

Идентификатор — UUID v4, он же попадает в свойство `message_id` AMQP и служит
ключом идемпотентности на стороне консьюмера.

## Transactional Outbox

Прямая публикация в брокер из сервиса создаёт классическую проблему: если
транзакция откатится после успешной публикации, подписчики обработают событие,
которого в базе нет. Если брокер недоступен — данные сохранятся, а событие
потеряется.

Решение: событие пишется в таблицу `outbox_message` **в той же транзакции**, что и
изменение данных.

```php
$transaction = $this->db->beginTransaction();
// UPDATE deal ...
// INSERT deal_stage_history ...
$this->publisher->publish(EventMessage::create(EventName::DEAL_STAGE_CHANGED, $payload));
$transaction->commit();
```

`$publisher` здесь — `OutboxEventPublisher`, он делает обычный `INSERT`. Привязка
интерфейса к реализации описана в `config/container.php`, поэтому сервис не знает,
что событие идёт через промежуточную таблицу.

Отдельный процесс переносит записи в брокер:

```bash
php yii outbox/relay
```

Воркер забирает пачку через `FOR UPDATE SKIP LOCKED`, публикует в `crm.events`,
проставляет `status = published` и `published_at`. При ошибке увеличивает `attempts`
и сохраняет текст в `last_error`; после пятой неудачной попытки запись переходит в
`failed` и перестаёт мешать остальным.

Гарантия доставки — **at least once**: одно и то же событие может уйти в брокер
повторно, если воркер упал между публикацией и коммитом. Дубли снимаются на стороне
консьюмера.

## Идемпотентность консьюмеров

Перед обработкой `EventDispatcher` вставляет пару `message_id + consumer` в таблицу
`processed_message` с уникальным индексом:

```php
if (!$this->markProcessed($message->id(), $consumer)) {
    return false;
}
```

Если вставка упала на нарушении уникальности — сообщение уже обрабатывалось этим
консьюмером, работа пропускается, сообщение подтверждается. Если обработка упала с
исключением, транзакция откатывается, запись из `processed_message` удаляется,
сообщение уходит в dead-letter очередь и может быть обработано повторно после
исправления причины.

Обратите внимание: ключ идемпотентности включает имя консьюмера. Одно событие
`deal.won` должно быть обработано и очередью уведомлений, и очередью аналитики —
но каждой ровно один раз.

## Обработчики

`NotificationHandler` создаёт запись в `notification` для ответственного менеджера
или автора задачи. `AnalyticsHandler` выполняет upsert в витрину `daily_stat`.

Оба реализуют `EventHandlerInterface` с методами `supports` и `handle`. Добавление
нового обработчика — это новый класс и одна строка в описании `EventDispatcher`
в `config/container.php`, без правки консьюмера.

## Запуск и наблюдение

```bash
php yii outbox/relay             # публикация событий из outbox
php yii consume/notifications    # обработка уведомлений
php yii consume/analytics        # обновление витрины статистики
php yii outbox/status            # сколько событий ждёт публикации
```

В Docker Compose эти три процесса подняты отдельными сервисами
(`worker-outbox`, `worker-notifications`, `worker-analytics`) с политикой
`restart: unless-stopped`.

Веб-интерфейс RabbitMQ доступен на http://localhost:15672 (логин `crm`, пароль `crm`).
Полезные признаки проблем:

- растёт `outboxPending` в `GET /api/health` — брокер недоступен или воркер публикации
  остановлен;
- растёт глубина очереди — консьюмер не справляется, можно поднять второй экземпляр;
- появились сообщения в `crm.dead-letter` — обработчик стабильно падает, смотрите
  логи в `backend/runtime/logs`.

## Проверка работы вручную

1. Войдите в интерфейс и перетащите карточку заказа на другую стадию.
2. Убедитесь, что запись появилась в outbox:
   `docker compose exec php php yii outbox/status`
3. Через пару секунд счётчик обнулится — воркер опубликовал событие.
4. В логах `docker compose logs worker-notifications` появится строка
   `deal.stage_changed обработано`.
5. В разделе «Уведомления» интерфейса появится новая запись.

Если запустить шаг 2 при остановленном RabbitMQ, счётчик будет расти, а после
поднятия брокера все накопленные события опубликуются — ничего не потеряется.
Это и есть смысл схемы с outbox.

## Настройка

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `RABBITMQ_HOST` | адрес брокера | `rabbitmq` |
| `RABBITMQ_PORT` | порт AMQP | `5672` |
| `RABBITMQ_USER` | пользователь | `crm` |
| `RABBITMQ_PASSWORD` | пароль | `crm` |
| `RABBITMQ_VHOST` | виртуальный хост | `/` |
| `OUTBOX_BATCH_SIZE` | размер пачки публикации | `100` |
| `OUTBOX_SLEEP_SECONDS` | пауза при пустой очереди | `2` |

Prefetch консьюмера задаётся флагом: `php yii consume/notifications --prefetch=20`.
